34/**
35 * Stats counter: tracks a histogram that summarizes, cumulatively, the numeric outcome of an event that keeps
36 * repeatedly happening. The performance profile of this tracking is as follows: record_value() performs a small
37 * number of comparisons and additions, plus an increment. All memory allocation occurs in the ctor.
38 *
39 * ### Thread safety ###
40 * It is thread-safe, in that all operations on a given `*this` may be invoked concurrently, excluding
41 * those that could change the bucket structure (as of this writing copy-assignment).
42 *
43 * All reads and writes are done using `std::atomic` with `memory_order_relaxed`, meaning one can (at least
44 * given Linux x86-64) expect similar performance to regular loads/stores sans `atomic<>`. (The `++` op, for
45 * x86-64 -- `x.fetch_add(1)` -- does take a few more cycles on an `atomic` than a naked `++` would; it is not
46 * the identical processor instruction. However the cycle cost difference is in the low-single-digit-ns range
47 * when uncontended: not identical but close. That pertains to record_value(). Cf.: loads (count_for_bucket())
48 * are fully identical.)
49 *
50 * Due to the nature of stat-keeping, `memory_order_relaxed` semantics are usually considered semantically acceptable.
51 *
52 * ### How it works ###
53 * record_value() records an event, updating the histogram data which are cumulative
54 * (there is no sliding time window; it just keeps accumulating stats). The histogram results-so-far can be viewed
55 * at will via `const` access.
56 *
57 * Each event is assumed to result in an integer-number outcome which one passes to record_value(). For example
58 * it might be a die throw; in which cases the possible outcomes are 1, 2, ..., 6. We accept *any* outcome
59 * as long as it fits into the large-range, signed type #value_t; whether there is really a constraint like
60 * 1-to-6, as with a die throw, is not our worry per se. Well, sort of; read on.
61 *
62 * In the ctor, a histogram-bucket array is initialized. This determines, forever (until destruction or copy-to),
63 * the outcome buckets. A count (starting at 0 and then potentially incremented by record_value()) is
64 * stored for each bucket. Of the buckets each represents a grouping of possible outcomes. (We discuss potential
65 * bucket sizes and such and how to configure this separately below; but here we stay general.)
66 *
67 * There shall be N (at least 2) buckets. All buckets are adjacent (there are no #value_t holes in-between).
68 * Each bucket has width that is at least 1 (no null buckets). Therefore each bucket can be represented as
69 * a combination of the following:
70 * - Min-value: To land in the bucket, the outcome must be *at least* min-value.
71 * - Width. This determines max-value: Min-value plus width minus 1. To land in the bucket, the outcome must be
72 * *at most* max-value. The next bucket, if any, begins at exactly max-value plus 1.
73 *
74 * This just leaves the aforementioned allowance of any input. Dice are not a great example for this, but just
75 * bear with us. Suppose you record_value() a number under first-bucket's min-value: in this case that's 1.
76 * Which bucket takes it? Answer: such an "underflow" always goes into first-bucket. So a "die throw" of 0
77 * or -12312 goes into first-bucket. Similarly, any value greater than or equal to X, where X is the min-value for
78 * last-bucket, lands into last-bucket (even if it exceeds last-bucket's max-value). A "die throw" of 7 or 321
79 * land in last-bucket, along with the vanilla last-bucket throw 6.
80 *
81 * @note You might notice that this in effect makes first-bucket's min-value and last-bucket's max-value
82 * irrelevant; as long as, when invoking ctor, it possible to express everything about the buckets except
83 * those two values, then it'll all work fine. Indeed: this is true. Nevertheless we require these
84 * things (one way or another) to still be specified. Reasons: First-bucket min-value provides a user-friendly
85 * "anchor point" of sorts, from which one can express various required points (e.g., first-bucket max-value,
86 * which is mandatory, can be expressed as min-value plus bucket-width minus 1). Last-bucket max-value
87 * is less useful in that sense but provides user-friendly symmetry (and the ability to detect overflow events
88 * in the future, if we come to desire this feature). Lastly, these values are -- again for user-friendliness
89 * reasons -- shown in the pretty-print output (`ostream<<` + to_ostream()).
90 *
91 * What about specific bucket structures supported by `*this`? In fact a `*this` supports any conceivable bucket
92 * structure, as long as the basic axioms are observed (to recap: at least 2, no null buckets, buckets are adjacent).
93 * In other words, the N buckets can be of any widths; e.g., they can be all different. The `vector`-taking
94 * ctor form supports this maximally-flexible config. However, there are different ctor forms for convenience
95 * and performance. We discuss these now.
96 *
97 * ### Bucket structure: Linear ###
98 * The simplest bucket structure supported is *linear*. In this setup, first-bucket can be of any specified
99 * width (as usual, not zero); while the remaining buckets (1+ of them) shall each have the same specified
100 * width. Therefore, the scale is generally linear, with a special-case potentially-different first-bucket.
101 *
102 * The rationale for offering this ctor form is not just convenience in the case where one happens to desire a
103 * linear scale. It is also, internally, handled differently w/r/t *performance*. If the bucket structure is
104 * linear, then the only computationally notable operation within record_value() et al -- given `value_t` outcome,
105 * find `size_t` bucket index of bucket containing that out come -- can be performed in constant time; no
106 * search through the buckets is required. record_value() can record stats inside tight loops in the middle
107 * of very perf-sensitive areas of one's application; the faster it is the better. This is therefore a significant
108 * win (when applicable).
109 *
110 * @note This constant-time-performance gain is in effect whenever the configured bucket structure supports it;
111 * it is not necessary to use that particular linear-scale ctor form. That is, if one uses the general
112 * (`vector`-taking) ctor form, and using that form specifies a linear-scale bucket structure, then
113 * `*this` will automatically use the faster lookup algorithm in record_value() et al.
114 *
115 * @note For the constant-time-performance gain to activate the requirement is as follows:
116 * Either there are exactly 2 buckets (degenerate case); or there are 3+, and all non-bookend buckets
117 * (i.e., all but first-bucket and last-bucket) have equal widths. (The linear-scale ctor form
118 * guarantees this; though in its case last-bucket also has the same width as the non-bookend buckets.)
119 *
120 * We demonstrate the linear-scale ctor's knobs with the die-throw example. `n_buckets` (ctor arg)
121 * is how many buckets there are. `bucket0_sz` is the "width" of first-bucket, and `bucket_sz` is the "width"
122 * of each of the other buckets including last-bucket. `bucket0_val0` is the min-value for first-bucket.
123 * - For example, with a die throw, you might use `n_buckets = 6` and `bucket0_sz = bucket_sz = bucket0_val0 = 1`.
124 * - The outcomes are then simply grouped as: [got 1][got 2][got 3][got 4][got 5][got 6].
125 * - Or you could do: `n_buckets = 3` and `bucket0_sz = bucket_sz = 2` and `bucket0_val0 = 1`.
126 * - The buckets are then: [got 1 or 2][got 3 or 4][got 5 or 6].
127 *
128 * This just leaves the aforementioned allowance of any input. Dice are not a great example for this, but just
129 * bear with us. Suppose you record_value() a number under `bucket0_val0`. Which bucket takes it? Answer:
130 * such an "underflow" always goes into first-bucket. So a "die throw" of 0 or -12312 goes into first-bucket.
131 * Similarly, any value greater than or equal to X, where X is the min-value for last-bucket, lands into last-bucket.
132 * - So consider `n_buckets = 3` and `bucket0_sz = bucket_sz = 2` and `bucket0_val0 = 1`. This *really* means
133 * the following actual buckets as viewed by `*this`:
134 * - [any value <= 2][3 or 4][any value >= 5].
135 * - In reality valid dice throws always result in 1 or 2 or ... or 6, so this happens to reduce to
136 * [1 or 2][3 or 4][5 or 6]. If "broken" dice throws are possible, though, then a `*this` stands ready
137 * to count them in the two edge buckets.
138 *
139 * ### Bucket structure: General ###
140 * Other than that, the general structure allows one to simply specify each bucket's width and min-value.
141 * The general-scale ctor form takes a `vector` (sized at least 2, the # of buckets); each bucket's min-value
142 * is that element (so they must be in strictly-increasing order). The only missing bit of info is the
143 * last-bucket's width (as there's no next-bucket to point at where this one ends); this is supplied as a separate
144 * ctor arg alongside the `vector`.
145 *
146 * Example: With die-throws, the general-scale ctor call would look like so:
147 * `Histogram_counter{{1, 2, 3, 4, 5, 6}, 1}`. Six buckets, with the given min-values; and the last bucket's
148 * width is 1.
149 *
150 * The performance of bucket-index-from-outcome lookup in record_value() et al is therefore as follows:
151 * - If 2 buckets: constant-time (degenerate case).
152 * - If 3+ buckets, and the non-bookend buckets are all of the same width: constant-time (see above).
153 * - Otherwise: logarithmic in bucket-count. The lookup is a straightforward binary search through
154 * the min-values `vector` supplied via ctor.
155 *
156 * @internal
157 * ### Impl notes ###
158 * Reading the ground-level comments should clarify ~all questions.
159 *
160 * One mechanical subtlety is that we use stat::load(), stat::store(), and stat::fetch_add() as our atomic ops.
161 * These are respectively simply:
162 * - `load(x)` is `x.load(memory_order_relaxed)`.
163 * - `store(&x, y)` is `x.store(y, memory_order_relaxed)`.
164 * - `fetch_add(&x, y)` is `x.fetch_add(y, memory_order_relaxed)`.
165 *
166 * We promised `memory_order_relaxed` perf and semantics; and those ops are available in flow::util::stat.
167 */

183 /**
184 * Allocates the histogram data structure (linear-scale: bucket widths [ABBB...]) and initializes each bucket's count
185 * to zero. Bucket widths [ABBB...] means that first-bucket can be of any positive length, while the remaining
186 * 1+ buckets are each of the same width which may or not equal first-bucket's.

188 * ### Performance ###
189 * This ctor form guarantees constant-time record_value(). See class doc header for a deeper dive.

191 * @see class doc header for overview of the arg knobs and the overall algorithm they control. Meanwhile
192 * the docs just below are formal with few-or-no expositional niceties.
193 *
194 * @param n_buckets
195 * Number of buckets (at least 2) in the histogram.
196 * @param bucket0_sz
197 * First-bucket shall count the following outcomes:
198 * less-than `bucket0_val0`, `bucket0_val0`, ..., `bucket0_val0 + bucket0_sz - 1`.
199 * `bucket0_sz` is at least 1.
200 * @param bucket_sz
201 * Each bucket except first-bucket and last-bucket shall count outcomes `X`, ..., `X + bucket_sz - 1`,
202 * where `X` is one plus the max-value of the preceding bucket.
203 * Last-bucket shall count outcomes `X`, `X + 1`, ... ad infinitum, where `X` is one plus the max-value of
204 * the preceding (next-to-last) bucket.

206 * @param bucket0_val0
207 * See above. Note that any value is allowed for `bucket0_val0`.

211 /**
212 * Allocates the histogram data structure (general-scale: bucket widths [ABCD...]) and initializes each bucket's
213 * count to zero. Bucket widths [ABCD...] means that each bucket's width can be any positive value, and
214 * they may (but are not required to) be all different.
215 *
216 * @note `bucket_val0s` can often be specified as a naked initializer-list sans any mention of `std::vector`;
217 * e.g.: `Histogram_counter histo{{1, 3, 5}, 2};`.
218 *
219 * ### Performance ###
220 * If all bucket widths, except possibly the first and last, are all equal -- or there are only 2 buckets total --
221 * this ctor form guarantees constant-time record_value(). Otherwise record_value() shall be logarithmic-time in
222 * the number of buckets. See class doc header for a deeper dive.
223 *
224 * @see class doc header for overview of the arg knobs and the overall algorithm they control. Meanwhile
225 * the docs just below are formal with few-or-no expositional niceties.
226 *
227 * @param bucket_val0s
228 * Vector (of size at least 2) indicating the min-values of each bucket in order; these must be in
229 * strictly increasing order. The max-value of the last bucket shall be
230 * `bucket_val0s.back() + bucket_n_sz - 1`.
231 * First-bucket shall *also* count all outcomes less-than its min-value (but to_ostream()
232 * will still specially show this min-value for expositional purposes).
233 * Last-bucket shall *also* count all outcomes greater-than the indicated max-value (but to_ostream()
234 * will still specially show this max-value for expositional purposes).
235 * @param bucket_n_sz
236 * Width (at least 1) of the last bucket; see formula just above.
237 */

257 /**
258 * Aggregator: bucket-by-bucket, makes `*this` bucket's count incremented by `src`'s corresponding bucket's
259 * count. That is: make `this->count_for_bucket(idx) == C(idx) + S(idx)`, where `C(idx)` is
260 * pre-condition `this->count_for_bucket(idx)`, and `S` is ditto for `src`.
261 *
262 * If `src` has a different structure than `*this`, behavior is undefined. Different structure means
263 * the following does not hold: same bucket count; for each respective bucket min-value and width are the same.
264 *
265 * Tip: To aggregate `N`=2+ `Histogram_counters`:
266 * - (Destructive) Take `auto& result = v[0]`; then for `idx` in [`1`, `N - 1`]: `result += v[idx]`.
267 * - (Non-destructive) Take `auto result = v[0]`; then for `idx` in [`1`, `N - 1`]: `result += v[idx]`.
268 *
269 * @param src
270 * One with same structure as `*this`. `this == &src` is allowed and will incur no special handling
271 * (hence the counts shall be doubled).
272 * @return `*this`.
273 */
274 Histogram_counter& operator+=(const Histogram_counter& src);
275
276 /**
277 * Delta: bucket-by-bucket, makes `*this` bucket's count decremented by `src`'s corresponding bucket's
278 * count. That is: make `this->count_for_bucket(idx) == C(idx) - S(idx)`, where `C(idx)` is
279 * pre-condition `this->count_for_bucket(idx)`, and `S` is ditto for `src`.
280 *
281 * @warning There is no underflow protection; if a given `C(idx) < S(idx)`, then post-condition
282 * `C(idx)` shall potentially *increase* in apparent value, potentially to an extremely high value
283 * indeed.
284 *
285 * If `src` has a different structure than `*this`, behavior is undefined. Different structure means
286 * the following does not hold: same bucket count; for each respective bucket min-value and width are the same.
287 *
288 * @param src
289 * One with same structure as `*this`. (`this == &src` is allowed and will incur no special handling
290 * (hence the counts shall be zeroed). Though in that case it's better to use clear().)
291 * @return `*this`.
292 */
293 Histogram_counter& operator-=(const Histogram_counter& src);

430 /**
431 * General bucket structure (except the last bucket's width): in strictly increasing order, each bucket's
432 * min-value. Not `const` to allow for copy-assignment at least.
433 *
434 * ### Use 1: Output ###
435 * There are two uses. First and least, it plus #m_bucket_n_sz are used in to_ostream() for user-friendly output,
436 * labeling the range of each bucket.
437 *
438 * ### Use 2: idx_of_outcome() ###
439 * More importantly it is used to implement idx_of_outcome(), used by record_value() et al to determine which
440 * bucket's count to increment, given an outcome belonging to one of said buckets. That is the central
441 * and only potentially time-consuming of the fast-path ops in a `*this`. The following cases are to be
442 * considered in order for a good combo of performance (top priority) and simplicity.
443 * -# If `size() == 2`:
444 * Only `m_bucket_val0s[1]` matters: Outcomes less-than this min-value are in bucket 0;
445 * else in bucket 1. Various corner cases can be ignored if we handle this particular degenerate case
446 * separately.
447 * - Time complexity: constant.
448 * -# If #m_linear_bucket_sz_or_0 is in effect (`!= 0`):
449 * This means all 1+ buckets strictly-between 1st and last are of the same width (vacuously so if `size() == 3`);
450 * namely `m_linear_bucket_sz_or_0`. Therefore an optimized algorithm for idx_of_outcome() is in effect; no search
451 * through buckets is required. Instead: if below `F = m_bucket_val0s[1]` => index 0; otherwise subtract `F`,
452 * divide by `m_linear_bucket_sz_or_0`, and add 1. The result, clipped against the ceiling `size() - 1`, is
453 * the index sought.
454 * - Time complexity: constant.
455 * -# General case:
456 * No particular optimization applies. Perform a binary-search through #m_bucket_val0s, clip against
457 * the range [`0`, `size()`), and voila.
458 * - Time complexity: logarithmic in size().
459 *
460 * ### Impl rationale: Why no `flat_map` instead of 2 `vector`s? ###
461 * We keep two equally-sized `vector`s: #m_bucket_val0s (the "labels": the bucket structure) and #m_per_bucket_counts
462 * (the counts in those respective buckets). `flat_map<value_t, atomic<count_t>>` would achieve essentially the
463 * same thing; in terms of time complexity of all our ops definitely the case. So should we use that instead?
464 *
465 * Firstly: yes, it would be quite defensible to do that. In terms of internal code quality, it would be more
466 * compact; things like `flat_map::upper_bound()` => iterator => deref directly in map => increment `.second`
467 * would read as tighter than the alternative -- a bit nicer. And the perf difference below, while real, is
468 * still pretty small.
469 *
470 * So why go with 2 `vector`s? Answer: basically it's a perf-maxing thing. record_value() et al can be and are
471 * used in extremely perf-sensitive tight loops, so potentially every processor cycle counts. The 2-`vector`
472 * setup has optimal cache-locality (#m_per_bucket_counts is what changes and is all in one area; #m_bucket_val0s
473 * is elsewhere and does not change after construction or copy-to). So by doing this we do guarantee the best
474 * perf achievable (in context).
475 *
476 * That said: Who says `flat_map` does not do it the same anyway? And, actually, it *sort of* does. In fact:
477 * `std::flat_map` is specified by the standard as an adapter that defaults to two internal containers
478 * `vector<Key>`, `vector<Mapped>` -- *exactly* what we have. However, as of this writing we are constrained
479 * by C++17; so we cannot use `std::flat_map`. What about `boost::container::flat_map` which originated `flat_map`
480 * in the first place, though? Answer: Interestingly, as of mid-2026, `boost::container::flat_map` is
481 * actually somewhat different from what the standard mandates for `std::flat_map`. It is not an adapter --
482 * its internal representation is hard-coded -- and looking inside there shows it deals in `pair<Key, Mapped>`;
483 * so most likely not keeping the keys and mapped-values segregated.
484 */
485 std::vector<value_t> m_bucket_val0s;

487 /**
488 * Bucket structure: an addendum to #m_bucket_val0s, this is the positive width of the last of size() buckets.
489 *
490 * ### Use ###
491 * It is used with #m_bucket_val0s in to_ostream() for user-friendly output.
492 *
493 * Note that it is *not* used in idx_of_outcome(), as any outcome not-below min-value of the last bucket
494 * is dumped into the last bucket. Again, though, it is nice for printing `*this`.
495 */
496 value_t m_bucket_n_sz;
497
498 /**
499 * If `size() == 2`, or the non-bookend buckets are not all of the same width, this is zero; else
500 * the (positive) width of each non-bookend bucket. In the latter case idx_of_outcome() may use the
501 * optimized non-degenerate constant-time algorithm that sidesteps the need to binary-search #m_bucket_val0s.
502 *
503 * @see #m_bucket_val0s doc header for an outline of the idx_of_outcome() algorithm, including how it
504 * aims to prominently use #m_linear_bucket_sz_or_0.
505 *
506 * ### Rationale ###
507 * Why keep this, given that (assuming it is not zero) it can be quickly computed
508 * as `(m_bucket_val0s[2] - m_bucket_val0s[1])`? Answer: For one thing, it acts as a flag to cache whether
509 * the non-bookend buckets are indeed all equal (walking #m_bucket_val0s each time would be linear-time and
510 * destroy the whole point of the intended optimization). Opportunistically, then, we might as well cache
511 * the aforementioned value to avoid the need for recomputing it; we've got to store the flag in any case so
512 * might as well cut down on repeated computations.
513 */
514 value_t m_linear_bucket_sz_or_0;
515
516 /**
517 * The data. Elements start at 0 and are incremented indefinitely; #count_t is too wide for overflow to be ever
518 * reached. `.size() >= 2`.
519 *
520 * Storing a `vector<atomic<>>` can be dodgy, in that it can be tough to even get it to compile, but in our case:
521 * - (Ignoring copy-assignment) It is constructed at its forever-`.capacity()` (and `.size()`) all the way
522 * until it is destroyed. No problems there.
523 * - Default copy-assignment would not compile; therefore our copy-assignment operator performs the required
524 * re-construction at the new capacity/size (explicitly); and then performs the required atomic-load-and-store
525 * ops (explicitly).
526 * - Copy-construction reuses this (again: default copy-assignment would not compile).
527 */
528 std::vector<std::atomic<count_t>> m_per_bucket_counts;
529}; // class Histogram_counter

535template<typename T>
536void Histogram_counter::record_value(T val)
537{
538 auto& count = m_per_bucket_counts[idx_of_outcome(static_cast<value_t>(val))];
539
540#if 1
541 fetch_add(&count, 1);
542
543 static_assert(sizeof(count_t) >= 8,
544 "We must use 64+-bit counters, so as to not need to contend with overflow.");
545#else // Pre-atomic<> code is here for posterity. With atomic<> the overflow case is just a pain, so we do the above.
546 if constexpr(sizeof(count_t) <= 4)
547 {
548 if (count != std::numeric_limits<count_t>::max()) // We promised to stop just before overflow.
549 {
550 ++count;
551 }
552 }
553 else
554 {
555 ++count; // In practice with 64+ bits in a count, it'll never overflow, so don't even worry about that.
556 }
557#endif
558}
