52Thread_local_ptr_cache::Global_tl_state::~Global_tl_state()
53{
54 /* The following is clearly harmless and clearly not-wrong: If this dtor is running, then obviously m_tlp_states_map
55 * cannot be accessed, so obviously the definitional condition "do not access Global_tl_state" becomes
56 * true. And if it is already `false`, then it's a no-op.
57 *
58 * Is it necessary? It is moot, per preceding paragraph, but it can't hurt to think about it.
59 * - If the boost::thread-module at_thread_exit() + tsp-cleanup phase runs before thread_local deinit
60 * (boost::thread thread): Flag will already be false. No-op. Not necessary.
61 * - If the boost::thread-module at_thread_exit() + tsp-cleanup phase runs after thread_local deinit
62 * (std::thread thread): thread_local deinit might run some dtor which could, e.g., use
63 * Tlp::get() for some entry. If this flag remained true here, but m_tlp_states_map is destroyed
64 * (which it will be just after this dtor {block} exits), then that Tlp::get() would try to read
65 * from an invalid map. Undefined behavior. So yes: necessary in this (contrived but possible) case.
66 * More to the point (contrived or not): would vanilla thread_specific_ptr happen to work OK? Yes:
67 * it would. (Relying on that is probably not so smart though -- in a boost::thread the tsp cleanup would
68 * have run already, so only for std::thread could it ever work -- but that's not our code; that's
69 * on the user. We should just mirror tsp as promised.) */
70 s_this_thread_global_tl_state_operative = false;
71}
